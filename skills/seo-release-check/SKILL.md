# SEO Release Check

Establish which public URLs should be discoverable, then verify that the application, HTTP responses, and discovery files agree. For a single URL, check it and its relevant variants directly. For a release, prioritize changed route families, high-value landing pages, and stable controls from the same templates. Run an audit read-only unless the user requests fixes.

## Verify the release

1. **Record intent.** Identify the environment, preferred origin, changed routes, and expected behavior for each representative URL. Include legacy aliases, intentional exclusions, and one missing page when route handling changed. Use a pre-release snapshot or verified Search Console landing pages if available. Use observed search entry traffic to support preserving existing utility routes. Keep unchanged, working routes out of release fixes unless evidence shows a regression or the user requests a change.
2. **Fetch and compare.** Use public GET requests and record status, redirect steps, canonical signals (HTML and HTTP), robots directives, and sitemap membership. Compare production with staging or a pre-release baseline when available. Follow redirects one hop at a time within the authorized scope. Record the observed final status and canonical for clean and relevant tagged variants, even when the destination returns the expected status. Preserve required redirect parameters independently of the canonical. Compare representative internal links with the intended destinations. For a soft 404, record the successful status and the missing-resource message or template marker in the body. Check robots.txt for the exact crawler and path. For Googlebot, select its specific group before evaluating rules and use the longest matching path, with Allow winning ties. Evaluate robots headers and meta directives for the crawler they name. Check serving restrictions such as an expired `unavailable_after` separately from `noindex`. A noindex directive needs crawling to be seen. Authentication protects private pages.
3. **Trace the evidence to source.** Locate the responsible route rule, layout, metadata helper, sitemap generator, or hosting configuration when code is available. For JavaScript or template changes, compare the served and rendered head on the same URL. Capture the response and crawl access of any script required to produce the expected metadata. When that comparison is required by the release and a render is unavailable, report it as unverified. For structured data, distinguish JSON syntax, visible content parity, and Google feature eligibility. For social previews, compare declared images in the server HTML and rendered head when both are available. Record asset status and media type, and confirm the file decodes when the release requires a usable image. Leave the actual platform preview and cache state unverified without platform evidence.
4. **Assess indexing and impact separately.** HTTP evidence can show what the server presents. Use Google Search Console URL Inspection for Google's indexed state and selected canonical. Label live inspection and indexed data separately. Compare traffic only across equivalent windows and relevant page, query, country, and device slices. If the evidence only covers the period before the release, say the post-release impact is unmeasured. Keep AI-crawler access and llms.txt discovery observations separate from search indexing and ranking.
5. **Report a release decision.** Give the environment and checked sample, then show each material finding with the affected URL, expected and observed signals, likely scope, source or next evidence, smallest fix, and retest. Prioritize unintended loss of access or search visibility. When choosing what to fix or preserve, cite the available landing-page click counts beside those decisions. Keep captured responses distinct from acceptance criteria for future retests. Call out working controls and intentional redirects or exclusions that passed. Use **Block** for a confirmed release defect, **Unverified** when required evidence is missing, or **Pass** when the stated release checks pass. Keep generic crawl advisories and unrequested platform checks out of the rollout decision. For a short report, give the verdict, use one table with a row per material issue, summarize passing controls together, and state material evidence gaps once.

For repeatable HTTP checks, read [the manifest guide](references/manifest.md) and use [the checker](scripts/check_release.py). It checks explicit HTTP expectations, including redirect location, canonicals, robots headers and media types. It also checks Googlebot's robots.txt access and sitemap membership. To gate browser metadata, capture the current rendered HTML and supply it to the checker. Review any remaining release requirements with the appropriate tools.

For migrations, traffic diagnosis, or disagreements between signals, read [release playbook](references/release-playbook.md).
